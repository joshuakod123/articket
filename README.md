# Articket — 티켓 다이어리

> 전시를 보고 나온 종이 한 장을, 버리지 않고 철해두는 앱.

미술관·갤러리·공연 관람 기록을 **커스텀 티켓**으로 만들고, 서류철에 철해
스크랩북처럼 꾸며 소장하는 Flutter 앱입니다. 기획서 v2.0의 Phase 1 화면이
전부 돌아가며, 계정·로컬 저장·탈퇴까지 기기 안에서 완결됩니다.
서버는 아직 없고, 계정과 티켓 모두 `shared_preferences`에 남습니다.

이미지 에셋이 **하나도 없습니다.** 종이 결, 서류철 질감, 티켓 타공, 스티커,
탭바 심볼까지 전부 `CustomPainter` / `Path`로 그립니다.

---

## 실행

```bash
flutter create . --project-name articket   # 플랫폼 폴더(android/ios) 생성
flutter pub get
flutter run
```

**Flutter 3.27 이상**이 필요합니다 (`Color.withValues`, `Color.toARGB32` 사용).

서체는 `google_fonts`가 첫 실행 때 네트워크로 받아옵니다. 오프라인 첫 빌드에서는
손글씨가 기본 서체로 잠깐 보일 수 있습니다.

```bash
flutter analyze
flutter test        # test/widget_test.dart — 스모크 테스트 5종
```

| 패키지 | 쓰임 |

| `crypto` | 비밀번호 해시 (기기 안에 평문을 두지 않기 위해) |

## 화면 지도

앱을 켜면 먼저 `AppGate`가 어느 화면을 보여줄지 정합니다. **화면을 밀지 않고
최상위 위젯 하나를 갈아 끼웁니다** — 로그아웃·탈퇴 시점에 스택이 몇 장 쌓였는지
따질 필요가 없어집니다.

```
   main.dart ──▶ AppGate  ─── AuthService 를 구독
                    │
       ┌────────────┼────────────────┐
  (읽는 중)     (로그아웃)        (로그인됨)
  SplashScreen  AuthScreen        RootShell
   브랜드 락업   로그인/회원가입
   + 조각 로더   한 화면 · 모드 전환
```

본 화면은 아래 탭바로 묶인 **세 화면**입니다 (`root_shell.dart`,
`IndexedStack`이라 탭을 오가도 스크롤 위치와 보던 달이 유지됩니다).

```
                    ┌──────────────┐
                    │  RootShell   │
                    └──────┬───────┘
        ┌──────────────────┼──────────────────┐
   [서랍 DRAWER]      [달력 CALENDAR]     [내 기록 RECORD]
  archive_screen     calendar_screen     profile_screen
        │
        │ 탭 → 표지가 젖혀 열림 (FolderOpenRoute)
        ▼
   folder_screen ─── 스크랩북 / 바인더 그리드 / 목록
        │
        ├─ 티켓 탭 ──▶ ticket_detail_screen ─┬─▶ editor_screen (티켓 위 꾸미기)
        │                                    ├─▶ record_sheet (감상 기록)
        │                                    ├─▶ ticket_style_sheet (프레임·포스터)
        │                                    └─▶ share_card_screen (9:16 내보내기)
        │
        ├─ 꾸미기 ───▶ page_decor_screen (페이지 꾸미기 · 티켓 자유 배치)
        └─ 공유 ─────▶ share_card_screen

   서랍에서 서류철 길게 누름 ──▶ folder_workbench (이름·서체·색·질감 작업대)

   내 기록 우상단 ⚙ ──▶ settings_screen ──▶ delete_account_screen (계정 영구 삭제)
```

## 화면별 핵심 구현

### 1. 서랍 — 가로 서류철 스택 (`archive_screen.dart`, `widgets/index_tab.dart`)

실제 파일 캐비닛처럼 서류철을 **가로로 눕혀 겹쳐 쌓았습니다.** 뒤 서류철이 앞
서류철 밑에 깔리며, 인덱스 탭이 3슬롯을 순환해 서로 가리지 않습니다.

- `FolderShape`(`CustomClipper<Path>`)로 위쪽 한 자리에 사다리꼴 탭을 깎고,
  `PhysicalShape`로 감싸 실루엣을 그대로 따라가는 그림자를 냅니다.
- 탭에는 서류철 이름이 **고른 필기구**(`FolderFont`)로, 몸통 왼쪽엔 최근 티켓의
  포스터 색을 채운 폴라로이드가 비뚤게 삐져나오고, 오른쪽엔 영문 라벨 · 보관 수 ·
  `FILE_01` 정리 번호가 찍힙니다.
- **길게 누르면** 서류철이 책상 위로 뽑혀 나옵니다 → `folder_workbench.dart`.

**헤더는 전시 도록의 표제지(title page)입니다.**

```
A R T I C K E T ──────────────────────── MMXXVI     ← 판권 줄 (연도는 로마 숫자)
═══════════════════════════════════════════════     ← 이중 괘선
───────────────────────────────────────────────

티켓 서랍                                    ┌───┐
THE TICKET DRAWER                           │ ＋ │  ← 황동 캡션 플레이트
───────────────────────────────────────────────
● 5 FILES · 6 TICKETS            FILED 2026.07.14
눌러서 펼치기 · 길게 누르면 고치기
```

배경에는 위쪽 가운데에서 떨어지는 조명(`RadialGradient`)을 한 겹 얹었습니다.
균일하게 밝은 벽은 미술관에 없습니다. 이 그라디언트 하나로 평면이 벽으로 읽힙니다.

### 2. 폴더 열림 전환 (`widgets/folder_open_route.dart`)

`PageRoute`를 커스텀 구현한 `FolderOpenRoute`. 서류철을 탭하면:

1. 눌린 카드의 화면 좌표를 `GlobalKey`로 읽고,
2. 그 자리에서 표지 복제본(`FolderCover`)이 **윗변을 축으로 `rotateX` 회전하며
   젖혀 열리고**, 동시에 카드 영역이 원근과 함께 화면 전체로 번져나가며,
3. 그 아래에서 스크랩북이 살짝 확대되며 차오릅니다.

뒤로 가면 역재생되어 표지가 다시 덮입니다. 모션 축소
(`MediaQuery.disableAnimations`) 사용자는 페이드만 받고, 좌표를 못 읽는 예외
상황에서는 기본 `MaterialPageRoute`로 폴백합니다.

### 3. 서류철 작업대 (`folder_workbench.dart`)

서류철을 만들거나 고치는 화면. 색 팔레트만 있던 걸 네 축으로 넓혔습니다.

| 축 | 선택지 |
|---|---|
| 이름 · 영문 라벨 | 자유 입력 (비우면 `FILE / 06` 자동) |
| 필기구 `FolderFont` | 다이모 라벨 · 타자기 · 도록 명조 · 손글씨 · 포스터 고딕 · 둥근 라벨 |
| 색 `tabColors` | 옥스블러드 · 올리브 · 네이비 · 마닐라 · 다크 크라프트 |
| 질감 `FolderTexture` | 크라프트지 · 리넨 클로스 · 가죽 · 마블 페이퍼 · 프레스보드 |

질감은 전부 `FolderSurface`가 `CustomPainter`로 찍습니다. 바탕색 → 결 →
빛 방향 그라디언트 → 가장자리 비네트 → 모서리 닳음 순서로 얹고, `seed`가 같으면
무늬도 같아서 같은 서류철은 다시 그려도 같은 얼룩을 유지합니다.

### 4. 서류철 내부 — 스크랩북 (`folder_screen.dart`, `widgets/scrap_page.dart`)

폴더를 열면 기본으로 스크랩북이 펼쳐집니다 (앱바 아이콘으로 `FolderView.book` →
`grid` → `list` 순환).

- `NotebookPage`: 크림 속지 + 옅은 모눈 점 + 왼쪽 제본 그늘과 실 박음질.
- 페이지를 넘기면 `PageView` + `rotateY`로 안쪽 제본을 축으로 살짝 젖혀집니다.
- **자동 배치** — 티켓이 두 장씩 마스킹 테이프(`WashiTape`, 톱니로 뜯긴 `ClipPath`)로
  비뚤게 붙고, 옆에 손글씨 메모(`ScrapMemo`)가 붙습니다:
  날짜 → 전시명 → 손그림 밑줄 → 한 줄 평 → 별점 · 장소.
- **자유 배치** (`folder.freeLayout`) — 꾸미기 화면에서 티켓을 처음 끌면 켜지고,
  이후 사용자가 앉힌 자리(`Ticket.px` / `py` / `pscale` / `protation`)에 그립니다.

### 5. 페이지 꾸미기 (`page_decor_screen.dart`)

스크랩북과 **똑같은 위젯**(`AutoScrapPage`, `TapedTicket`, `NotebookPage`)을 써서,
여기서 본 그림이 완성된 페이지와 일치합니다. 티켓을 끌면 자유 배치로 전환되고
두 손가락으로 돌리고 키웁니다. 붙이는 것들은 `scrap_sheets.dart`에서 고릅니다.

### 6. 티켓 (`widgets/ticket_card.dart`, `frame_shapes.dart`)

프레임 6종을 이미지 에셋 없이 `Path.combine`으로 타공·톱니·퍼포레이션을 뚫어
표현합니다.

| 프레임 | 실루엣 | 비율 | 절취선 |
|---|---|---|---|

## 크기를 다루는 규칙 — `ScaledCanvas`

이 앱에서 반복해서 터졌던 버그가 하나 있습니다. **같은 그림을 다른 크기 상자에
넣을 때 레이아웃이 다시 흐르는 것**입니다. 티켓은 상자에 맞춰 작아지는데
글자 크기(13.5pt)와 여백(18pt)은 그대로라, 결과적으로 글자만 거대해집니다.

그래서 규칙을 하나로 못 박았습니다.

> **인쇄물처럼 보여야 하는 것은, 고정 설계 크기로 한 번 그린 뒤 통째로 축척한다.**

`widgets/scaled_canvas.dart`가 그 역할을 합니다.

```dart
ScaledCanvas(
  design: const Size(360, 640),   // 이 크기 기준으로 글자·여백을 정함
  child: _Card(...),              // 상자가 아무리 작아져도 그림은 동일
)
```

| 자리 | 설계 크기 |
|---|---|
| 공유 카드 전체 | 360 × 640 (9:16) |
| 스크랩북 페이지 (공유) | 340 × 472 |
| 티켓 한 장 (공유) | 300 × (300 / `frame.aspect`) |
| 티켓 + 레이어 | `ticketDesignWidth` (`ticket_canvas.dart`) |

안쪽에서 `MediaQuery.withNoTextScaling`으로 시스템 글자 배율도 끊습니다.
인쇄물이 접근성 설정에 따라 판이 바뀌면 안 되니까요.

내보내기는 `ShareCard.captureToFile(targetWidth: 1080)`로 화면에 그려진 크기와
무관하게 **항상 1080 × 1920**으로 뜹니다.

### `PrintBox` — 비율은 위젯이 지킨다

`ScaledCanvas`는 "이 상자에 맞춰 통째로 줄여라"까지만 합니다. 어떤 상자가
들어올지는 호출부 책임입니다. 티켓에서는 그게 문제였습니다.

예전 `TicketFront` · `TicketCanvas`는 이렇게 그렸습니다.

```dart
SizedBox(
  width: c.maxWidth,      // 부모가 준 상자 그대로
  height: c.maxHeight,
  child: FittedBox(
    fit: BoxFit.fill,     // ← 가로·세로 배율을 따로 잡음
    child: SizedBox(width: 300, height: 300 / aspect, child: ...),
  ),
)
```

`BoxFit.fill`은 두 축의 배율을 **따로** 계산합니다. 부모가 준 상자의 비율이
티켓 비율과 조금이라도 다르면 그 차이가 그대로 왜곡으로 나옵니다.
지금까지는 호출부가 전부 `AspectRatio`로 감싸 준 덕분에 우연히 맞았을 뿐이고,
아래 세 자리에서 그 전제가 깨집니다.

- **Hero 비행 중** — 오버레이가 출발 사각형과 도착 사각형을 보간해 물립니다.
  중간 프레임의 비율은 어느 쪽과도 다릅니다.
- **tight 제약 아래** — `AspectRatio`는 `constraints.isTight`이면 계산을 포기하고
  `constraints.smallest`를 그대로 돌려줍니다. 즉 `Positioned.fill`,
  `SizedBox.expand` 밑에서는 **아무 일도 하지 않습니다.**
- 호출부가 하나라도 `AspectRatio`를 빠뜨리는 순간.

`widgets/print_box.dart`는 규칙을 뒤집습니다.

> **비율은 위젯 자신이 지키고, 부모는 최대 크기만 알려준다.**

```dart
PrintBox(
  design: Size(300, 300 / ticket.frame.aspect),
  clipBehavior: Clip.none,        // 스티커가 삐져나오는 게 자연스러운 자리
  child: ...,
)
```

안에서 비율을 지키는 가장 큰 사각형을 직접 구한 뒤, **그 크기의 상자에만**
`BoxFit.fill`을 씁니다. 이 시점에는 상자와 원도의 비율이 정확히 같으므로
두 축의 배율이 동일합니다. `Align`을 한 겹 두어 부모가 tight 제약을 걸어도
안쪽에서 다시 비율을 잡을 수 있게 했습니다 (`Align`은 자식에게 loose를 넘깁니다).

같은 파일의 `FittedParagraph`는 남은 높이에 **줄 단위로** 본문을 흘립니다.
예전 티켓 뒷면은 감상문을 `Expanded` + `TextOverflow.fade`로 그렸는데,
남은 높이가 두 줄 반이면 세 번째 줄이 **글자 중간에서 잘려** 아래 `WITH` 줄과
겹쳐 보였습니다. 이제 실제 줄 높이로 몇 줄이 들어가는지 세어 `maxLines`를
정하므로 반 줄이 남지 않고, 넘치면 말줄임표로 끝납니다.

## 저장소 API (`data/ticket_store.dart`)

`ChangeNotifier` 싱글턴 하나가 전부입니다. 화면은 `ListenableBuilder`로 이
객체만 구독하므로, **저장 계층만 갈아 끼우면** 화면 코드는 손댈 필요가 없습니다.

지금은 `data/local_store.dart`(SharedPreferences)를 씁니다. 스키마가 커지면
`LocalStore`의 `readMap` · `write` 두 메서드만 Hive/Isar 호출로 바꾸면 됩니다.

| 메서드 | 동작 |
|---|---|
| `load()` | 앱 시작에 한 번. 기기에서 읽고, 첫 실행이면 예시를 깝니다 |
| `isReady` | `load()`가 끝났는지. `AppGate`가 봅니다 |
| `folders` / `tickets` | 읽기 전용 목록 |
| `ticketsIn(folderId)` | 폴더 안 티켓 (최신순) |
| `countIn` / `byId` / `folderById` | 조회 |
| `addFolder` / `removeFolder` | 서류철 추가 / 삭제 (안의 티켓도 함께) |
| `add(ticket)` | 티켓 추가. **이 자리에서 발권 번호가 한 번 찍힙니다** |
| `remove(id)` | 티켓 삭제. 번호는 회수하지 않습니다 |
| `previewSerial(date)` | 다음에 찍힐 번호 미리보기 |
| `addLayer` / `removeLayer` / `bringToFront` | 스크랩 레이어 |
| `touch()` | 가변 필드만 바꿨을 때 갱신 알림 + 저장 |
| `wipe()` | 탈퇴. 메모리와 기기 양쪽을 비웁니다 |

`Ticket`과 `ArchiveFolder`는 **가변 객체**입니다. 필드를 직접 쓴 뒤 `touch()`를
부르는 방식이라, 시트에 저장 버튼이 따로 없고 고르는 즉시 반영됩니다.

### 예시 데이터를 되살리지 않는 이유

`load()`는 `seeded` 플래그를 따로 봅니다. "폴더도 티켓도 비었으면 예시를 깐다"만
쓰면, 사용자가 예시를 전부 지우고 앱을 다시 켰을 때 **예시가 되살아납니다.**
지운 것이 돌아오는 건 저장소가 깨졌다는 신호로 읽힙니다.

## 발권 번호 (`data/serial.dart`)

티켓 하나에 하나씩 찍히는 `AK-2026-014` 번호입니다. 두 번 고쳤습니다.

**1차 — 흩어진 규칙을 모음.** 번호를 만드는 자리가 목업 · 서랍 화면 · 프로필
세 군데였습니다. 서로 다른 규칙이 동시에 돌아서, 2026년 첫 관람인데 번호가
`00114`이고 회원 번호가 티켓을 추가할 때마다 바뀌었습니다. 전부 `TicketStore`로
모았습니다.

**2차 — 다시 매기지 않게 함.** 1차에서는 번호를 "저장하는 값"이 아니라
"데이터에서 뽑아내는 값"으로 만들었습니다. 목록이 바뀌면 전체를 다시 매겼습니다.
의도는 좋았지만 발권 번호로는 틀린 선택이었습니다.

- 3번 티켓을 버리면 **4번이 3번이 됩니다.** 이미 공유 카드로 내보낸
  `AK-2026-004`가 세상 어디에도 없는 번호가 됩니다.
- 관람일을 하루 고치면 그날 이후 번호가 **줄줄이 밀립니다.**

실물 발권기는 찍는 순간 번호를 확정하고, 그 표를 버려도 그 번호를 다시 쓰지
않습니다. 지금은 같습니다.

| 규칙 | 내용 |
|---|---|
| 언제 찍히나 | `TicketStore.add()` 딱 한 번 |
| 무엇이 저장되나 | 문자열이 아니라 `Ticket.issuedYear` · `issuedSeq` 두 정수 |
| 연도 | **관람한 해**. 나중에 관람일을 고쳐도 번호는 그대로 |
| 순번 | 그 해의 **최고값 + 1**. 지운 번호는 되쓰지 않음 |
| 구버전 데이터 | `parseTicketSerial()`이 문자열에서 되읽어 이관 |

목록에 `AK-2026-003` 다음이 `AK-2026-005`인 구간이 생길 수 있습니다. 그게
맞습니다. 표를 한 장 버린 티켓북은 원래 그렇게 생겼습니다.

회원 번호(`M-2025-0006`)는 **일부러 다른 모양**입니다. 둘 다 `AK-` 꼴이면
프로필의 번호가 티켓 번호처럼 읽혀서 "이건 뭐지?" 하게 됩니다. 시작 연도에서만
뽑으므로 티켓을 추가해도 바뀌지 않습니다.

## 계정과 탈퇴 (`services/auth_service.dart`)

서버가 아직 없으므로 계정도 기기 안에 둡니다. 비밀번호는 평문으로 두지 않고
**임의 소금 + SHA-256**으로 해싱합니다. 기기 안이라도 평문을 남기면 백업 파일이
새는 순간 사용자가 다른 서비스에서 쓰는 비밀번호까지 같이 샙니다.

로그인 실패 시 "없는 이메일"과 "틀린 비밀번호"를 **구분해서 알려주지 않습니다.**
그 이메일이 가입돼 있다는 사실 자체가 계정 열거 공격의 실마리입니다.

서버가 생기면 아래 네 메서드의 **본문만** 갈아 끼우면 됩니다.

| 메서드 | 서버판 |
|---|---|
| `signUp` | `POST /auth/signup` |
| `signIn` | `POST /auth/login` (+ 토큰 저장) |
| `signOut` | 토큰 폐기 |
| `deleteAccount` | `DELETE /auth/me` → **성공 응답 뒤에** 로컬 삭제 |

### App Store Guideline 5.1.1(v)

계정을 만들 수 있는 앱은 **앱 안에서** 계정을 영구 삭제할 수 있어야 합니다.
자주 걸리는 네 가지:

1. 웹 페이지로 보내거나 "고객센터에 문의"로 넘기면 **리젝**입니다.
2. 비활성화(deactivate)만 제공하는 것도 안 됩니다. 계정과 그에 딸린 데이터가
   실제로 지워져야 합니다.
3. **설정 깊숙이 숨겨도 지적받습니다.** 지금은 설정 첫 화면에서 한 번만 누르면
   닿습니다.
4. 나중에 구글/카카오/네이버 로그인을 붙이면 **Sign in with Apple**도 같이
   제공해야 합니다(4.8). 지금은 이메일 하나뿐이라 해당 없음.

`delete_account_screen.dart`는 다이얼로그 대신 화면을 통째로 씁니다. "확인"은
습관적으로 눌리는데 이건 되돌릴 수 없기 때문입니다.

1. **무엇이 사라지는지 숫자로** 보여줍니다. "티켓 6장"은 "모든 데이터"보다
   훨씬 무겁게 읽힙니다.
2. 안내 문구를 **손으로 따라 적습니다.** 오타 없이 적으려면 문장을 읽어야 합니다.
3. 마지막으로 비밀번호. 잠금 해제된 기기를 남이 집어 든 경우를 막습니다.

삭제 순서는 **데이터 먼저, 계정 마지막**입니다. 반대로 하면 중간에 앱이 죽었을 때
"계정은 없는데 기록만 남은" 상태가 됩니다. 그 기록은 누구도 다시 열 수 없고
지울 수도 없습니다.

|---|---|
| `ArticketLoadingView` | 화면 전체가 비어 있는 동안 |
| `InlineLoader` | 카드 · 시트 안의 작은 자리 |
| `runWithLoader(context, task:)` | 오래 걸리는 작업을 감싸는 모달 |

`runWithLoader`는 **150ms 안에 끝나는 작업에는 막을 아예 띄우지 않습니다.**
깜빡임이 기다림보다 더 거슬리기 때문입니다. 막이 떠 있는 동안 뒤로 가기를
막고(`PopScope`), 예외가 나도 `finally`에서 반드시 걷습니다.

## 함정 노트

이 프로젝트에서 실제로 터졌던 것들입니다. 같은 실수를 반복하지 않으려고 적어 둡니다.

**`Flexible`은 자리가 모자라면 겹칩니다.** `Flexible(child: Text(...))`에 남은
높이가 0이면, 프레임워크는 "높이 0"이라고 통보하지만 `Text`는 제 높이대로
그려집니다. 결과적으로 **다음 형제가 그 위에 겹쳐 찍힙니다.** 잘린 게 아니라
덮인 겁니다. 좁아질 수 있는 텍스트 묶음은 `Flexible` 대신 자연 높이로 두고
`FittedBox(fit: BoxFit.scaleDown)`으로 통째로 줄이세요.

**`await showDialog`는 다이얼로그가 사라지기 전에 풀립니다.** `Navigator.pop`이
불린 순간 `await`가 풀리지만 닫히는 애니메이션이 150ms 남아 있고, 그동안
`TextField`는 살아서 컨트롤러를 듣고 있습니다. 거기서 `controller.dispose()`를
부르면 `deactivate` 순회가 예외로 끊기고, 끝내 `assert(_dependents.isEmpty)`로
앱이 죽습니다. **컨트롤러는 항상 그걸 쓰는 `State`가 만들고 `State.dispose()`에서
버리세요.**

**`CrossAxisAlignment.stretch`는 스크롤 뷰 안에서 무한 높이를 부릅니다.**
세로 스크롤이 자식에게 주는 높이는 무한대라, stretch가 그대로 물리면 카드가
"높이 = 무한"이 됩니다. `AspectRatio`나 `SizedBox`로 높이를 못 박으세요.

**레이어 좌표는 픽셀이 아니라 캔버스 대비 0.0~1.0 비율입니다.** 기기 화면이
달라져도 배치가 유지되고, 그대로 서버에 올릴 수 있습니다.

**`posterPath`는 기기 로컬 캐시 경로입니다.** 앱을 재설치하면 사라지므로, 실제
저장 단계에서는 사진을 앱 문서 디렉터리로 복사해 두어야 합니다. 웹에서는
`Image.file`을 쓸 수 없어 색으로 폴백합니다.

**자이로는 없는 기기가 많습니다.** `sensors_plus` 호출을 `try/catch`로 감쌌고,
데스크톱·웹·시뮬레이터에서는 홀로그램이 정지 상태로 보입니다.

**접근성.** `MediaQuery.disableAnimations`가 켜져 있으면 티켓 플립과 폴더 열림
전환 둘 다 애니메이션을 건너뜁니다.

**`WallGrain`은 이미 `Positioned.fill`을 품고 있습니다.** `Stack`에 넣을 때
`Positioned.fill(child: WallGrain(...))`로 한 번 더 감싸면 같은
`RenderObject`에 `StackParentData`를 쓰는 위젯이 둘 붙어
`Incorrect use of ParentDataWidget`이 뜹니다. **맨몸으로** 넣으세요.

**`CrossAxisAlignment.stretch`는 가로 `Row`에서도 위험합니다.** 세로 스크롤
얘기만이 아닙니다. `Row`의 stretch는 "부모가 준 **높이**를 자식에게 그대로
물려라"라는 뜻입니다. 높이가 무한인 자리(`Positioned`에 `top`이 없는 토스트 등)
아래에서는 그대로 `h=Infinity`가 됩니다. 왼쪽 색 띠를 본문 높이만큼 늘리려면
`IntrinsicHeight`로 감싸 자식들의 자연 높이를 먼저 재게 하세요.

**`pubspec.yaml`의 `assets:` 블록을 주석 처리해 두면 조용히 실패합니다.**
파일을 `assets/`에 넣어 두어도 번들에 들어가지 않고, `Image.asset`은 실행 중에
회색 상자가 됩니다. 빌드는 성공하므로 아무도 알려주지 않습니다.

**고정 여백 + 폰트 실측 폭 = 화면 밖.** `TitlePlateLogo`의 좌우 여백은
`46 * scale`로 고정인데 안쪽 워드마크 폭은 Bodoni의 글자 실측치라 기기·글꼴
로딩 상태에 따라 달라집니다. 둘을 더한 값이 화면 폭을 넘으면 액자가 가장자리에
딱 붙습니다. **`Padding`을 바깥에, `FittedBox(scaleDown)`을 안쪽에** 두세요.
반대로 하면 여백까지 같이 축소돼서 결국 또 붙습니다.

**부팅 `Future`의 예외는 화면을 영구히 붙잡습니다.** `AppGate._boot()`이
`Future.wait`에서 던지면 `_held = true`가 실행되지 않아 스플래시에서 나올 수
없습니다. 사용자 입장에서는 "앱이 안 켜짐"입니다. `try/finally`로 감싸
저장소가 실패해도 최소한 로그인 화면까지는 가게 하세요. (새 플러그인을 추가한 뒤
hot restart만 하면 `MissingPluginException`으로 이 경로를 정확히 밟습니다)

# 제품 방향 — 열어둔 질문들

여기부터는 확정된 계획이 아니라 **결정을 미뤄둔 항목과 그 근거**입니다.
순서대로 읽으면 왜 이 순서로 만들어야 하는지가 드러납니다.

## 0. 먼저 해야 하는 것 — 전시 마스터 DB

아래 네 가지가 전부 이것 위에 올라갑니다. **지금 안 하면 나중에 못 합니다.**

지금 `Ticket.title`과 `venue`는 자유 입력 문자열입니다. 그래서 같은 전시가
이렇게 갈립니다.

```
"Claude Monet Water Lilies" / "국립현대미술관 서울"
"모네 수련"                  / "MMCA 서울"
"모네: 수련 연작"            / "국현 서울관"
```

사람이 보면 같은 전시지만 기계는 셋을 다른 것으로 셉니다. 그러면

- 커뮤니티에서 "이 전시를 본 사람들"을 모을 수 없고,
- 매거진에서 "올해 가장 많이 간 미술관"을 셀 수 없고,
- 마켓에서 "이 전시 전용 스티커 팩"을 붙일 데가 없습니다.

**해야 할 것**

| 항목 | 내용 |
|---|---|
| 스키마 | `exhibitions(id, title_ko, title_en, venue_id, start_at, end_at, poster_url)` |
| 입력 | 티켓 만들 때 자동완성. 목록에 없으면 자유 입력 + "새 전시 제안"으로 큐에 쌓기 |
| 마이그레이션 | `Ticket`에 `exhibitionId` **nullable**로 추가. 기존 티켓은 null 유지 |
| 초기 데이터 | 문체부/예술경영지원센터 공연예술통합전산망, 각 미술관 RSS, 수동 시딩 |

`exhibitionId`를 nullable로 두는 게 핵심입니다. "반드시 마스터에서 골라야 함"으로
만들면, 목록에 없는 소규모 갤러리를 기록하려던 사용자가 그 자리에서 이탈합니다.
자유 입력을 남겨두고 **나중에 매칭**하세요.

## 1. 커뮤니티 — "자랑"을 어디에 둘 것인가

> *커뮤니티를 만들어서 자랑해야하나..? 커뮤니티 공유 방안으로 더 활성화?*

### 결론부터

**독립 피드는 만들지 마세요.** 대신 두 갈래로 갑니다.

1. **밖으로** — 인스타 스토리 공유를 유입 장치로 (이미 90% 구현됨)
2. **안으로** — 사람이 아니라 **전시**를 허브로

### 왜 독립 피드가 위험한가

앱 내 피드는 콜드 스타트가 잔인합니다. 팔로우 그래프를 처음부터 쌓아야 하는데,
Articket 사용자는 **한 달에 한두 번** 전시를 봅니다. 매일 열 이유가 없는 앱에
피드를 붙이면 늘 텅 비어 있고, 텅 빈 피드는 앱이 죽었다는 신호로 읽힙니다.
게다가 피드에는 신고·차단·모더레이션이 딸려 옵니다. 1인 개발로 감당할 표면적이
아닙니다.

### 대신 — 전시가 허브

같은 전시를 본 사람들의 티켓이 한 페이지에 모이는 구조입니다.

```
  전시 페이지 — "Claude Monet: Water Lilies"
  국립현대미술관 서울 · 2026.05.01 – 08.31

  ★ 4.3  (기록 128장)
  ┌──────┬──────┬──────┬──────┐
  │티켓  │티켓  │티켓  │티켓  │   ← 다른 사람이 만든 티켓 (공개 설정한 것만)
  └──────┴──────┴──────┴──────┘
  한 줄 평 몇 개
```

이게 나은 이유:

- **콜드 스타트가 없습니다.** 첫 사용자도 전시 이름만 있으면 페이지가 성립합니다.
- **검색 유입이 생깁니다.** "모네 전시 후기"를 검색한 사람이 웹 버전 전시
  페이지로 들어옵니다. 앱 내 피드는 구글에 안 잡힙니다.
- **자랑의 동기가 자연스럽습니다.** 내 티켓이 그 전시 페이지에 걸리는 것 자체가
  보상입니다. 팔로워 수를 세지 않아도 됩니다.
- 모더레이션 표면이 작습니다. 텍스트는 한 줄 평뿐입니다.

### 밖으로 — 지금 바로 할 수 있는 것

`share_card_screen`이 이미 1080×1920 PNG를 뽑습니다. 여기에 두 줄만 더하면
유입 장치가 됩니다.

| 추가 | 이유 |
|---|---|
| 카드 하단에 **작은 워드마크 + 전시 페이지 딥링크 QR/문구** | 본 사람이 찾아올 경로 |
| `share_plus`에 텍스트 동봉 (`전시명 · articket.app/e/{id}`) | 인스타는 캡션이 검색됨 |
| 웹 전시 페이지에 OG 이미지 | 링크 미리보기가 티켓으로 뜸 |

워터마크는 **아주 작게**. 크면 사용자가 카드를 안 올립니다.

### 공개 범위

기본값은 **비공개**여야 합니다. 이 앱은 "혼자 소장하는 서랍"으로 팔리고 있고,
기본 공개는 그 약속을 깹니다. 티켓 단위로 `isPublic` 토글을 두고, 처음 켤 때
"이 티켓이 전시 페이지에 걸립니다"를 명확히 보여주세요.

## 2. 크리에이터 마켓 — 올리고 사고 적용하기

> *사람들이 디자인을 만들어서 올릴꺼면, 그걸 어떻게 올리고 그걸 산 유저는
> 어떻게 적용시킬지도 고민해봐야할 문제*

### 지금 구조가 유리한 점

이 앱은 **이미지 에셋이 하나도 없습니다.** 전부 `CustomPainter`와 `Path`입니다.
그래서 "디자인 하나"는 바이너리가 아니라 **JSON 수십 줄**입니다.

```json
{
  "schema": 1,
  "kind": "ticket_preset",
  "frame": "stub",
  "posterTint": ["0xFF3B2E5A", "0xFF15102A"],
  "layers": "[{...ScrapLayer.encodeList 결과...}]"
}
```

전송량이 작고, 검열하기 쉽고, 버전 관리가 됩니다. `ScrapLayer.encodeList`가
이미 있으니 절반은 되어 있습니다.

### 문제 — 새 그림을 못 그립니다

`StickerArt` 16종은 앱 바이너리 안에 `Path`로 박혀 있습니다. 크리에이터는
**이미 있는 것을 재조합**할 수만 있습니다. 그건 마켓이 아니라 프리셋 공유입니다.

그래서 판매 단위를 세 등급으로 나눠서 봐야 합니다.

| 등급 | 무엇 | 저장 형태 | 난이도 | 언제 |
|---|---|---|---|---|
| **A. 프리셋** | 기존 요소의 배치·색·서체 조합 | JSON | 낮음 — 지금 구조로 바로 | 먼저 |
| **B. 팔레트/질감** | 새 색 조합, 종이결 파라미터 | JSON (숫자) | 낮음 | 먼저 |
| **C. 에셋** | 새 스티커·도장·프레임 | SVG | 중간 — 렌더러 필요 | 나중 |

**A·B로 시작하세요.** 서버·결제·모더레이션 파이프라인을 A·B로 먼저 돌려보고,
거래가 실제로 일어나는 걸 확인한 뒤에 C를 엽니다.

### C를 열 때 필요한 것

- **`flutter_svg`** 도입. 단, SVG는 임의 콘텐츠입니다. `<script>`, `<image href>`
  외부 참조, 거대한 path를 서버에서 **정제(sanitize)** 하고, 실패하면 반려.
- **크기 상한**. path 노드 수 · 파일 크기 · 렌더 시간 상한을 두세요. 없으면
  누군가 10만 노드짜리 SVG를 올려서 스크랩북 페이지를 60fps에서 3fps로 만듭니다.
- **래스터 폴백**. 서버에서 512px PNG를 같이 구워 두고, SVG 렌더가 실패하거나
  썸네일이 필요한 자리에서 씁니다.

### 적용(설치) 흐름

```
구매  →  서버가 서명된 팩 JSON 반환
      →  로컬 installed_packs 에 저장 (팩 id · 버전 · 만료 없음)
      →  스티커 시트 / 프레임 시트가 "내장 + 설치된 팩"을 합쳐서 표시
      →  사용자가 티켓에 얹음 → layer.content 에 "pack:{packId}/{assetId}" 로 참조
```

**여기서 반드시 정해야 하는 두 가지**

1. **에셋 id는 절대 바뀌면 안 됩니다.** 팩 안의 `star_01`을 v1.3에서
   `star_gold`로 이름 바꾸면, 그걸 붙여둔 모든 티켓이 깨집니다. id 레지스트리는
   append-only로 두고 표시 이름만 바꾸세요.
2. **팩을 지우면 그 팩을 쓴 티켓은 어떻게 되나?** 세 선택지 중 하나를 고르고
   문서에 박아두세요.
  - (a) 구매한 팩은 삭제 불가 — 가장 단순, 저장 공간을 먹음
  - (b) 지우면 해당 레이어가 회색 자리표시로 — 정직하지만 보기 흉함
  - (c) 티켓에 얹는 순간 팩 에셋을 **티켓 안으로 복사**(embed) — 저장은 커지지만
    팩과 티켓이 독립. **개인적으로 (c)를 권합니다.** 실물 스티커도 한 번 붙이면
    스티커북을 버려도 남습니다.

### 수익 배분의 현실

앱스토어에서 디지털 재화는 **애플이 30%**를 먼저 가져갑니다(소규모 사업자
프로그램이면 15%). 크리에이터에게 50%를 주기로 하면:

```
사용자 결제 ₩3,000
  − 애플 30%      ₩900
  = ₩2,100
  − 크리에이터 50% (판매가 기준 ₩1,500)
  = ₩600  ← 실제 수익 20%
```

"판매가의 50%"인지 "정산액의 50%"인지를 처음부터 명시하세요. 나중에 바꾸면
크리에이터가 떠납니다. 그리고 크리에이터 정산은 **원천징수와 사업소득 신고**가
붙습니다. 개인에게 지급하면 3.3% 원천징수 의무가 생깁니다.

### 가장 큰 리스크는 기술이 아니라 저작권

사람들은 **실제 전시 포스터, 캐릭터, 브랜드 로고**를 올립니다. 확실히 옵니다.
- 업로드 시 "본인이 직접 만든 것" 체크 + 신고 창구 + DMCA 대응 절차를 처음부터.
- 자동: 지각 해시(pHash)로 알려진 포스터 DB와 대조, NSFW 분류기.
- 수동: 승인 큐. 자동 통과 없이 사람이 한 번 보는 게 초기에는 훨씬 쌉니다.

## 3. 개인 매거진 내보내기

> *나중에는 개인 메거진처럼 내보낼 수 있도록 (보그 잡지의 미감이 너무 이뻤다)*

### 이게 가장 자연스러운 다음 단계입니다

이유가 셋입니다.

1. **기술적으로 이미 절반 있습니다.** `ScaledCanvas`(고정 설계 크기)와
   `RepaintBoundary → PNG`가 돌아갑니다. 매거진은 그걸 **여러 장 + PDF**로
   확장한 것입니다.
2. **서체가 이미 맞습니다.** Vogue의 마스트헤드는 Didone 계열이고,
   이 앱의 `wordmark`/`plate`가 **Bodoni Moda**입니다. 우연이 아니라 같은 계보입니다.
3. **아래 4번(실물 인쇄)의 전제**입니다. 매거진 PDF를 만들 수 있어야 인쇄를 겁니다.

### Vogue 미감을 규칙으로 옮기면

"예쁘다"를 코드로 옮기려면 규칙이 필요합니다. 관찰되는 것 다섯 가지:

| 장치 | 구현 |
|---|---|
| **극단적 크기 대비** | 전면 이미지 옆에 8pt 캡션. 중간 크기를 쓰지 않음 |
| **여백이 콘텐츠** | 페이지의 40% 이상을 비움. 바깥 여백을 안쪽보다 넓게 |
| **그리드 이탈** | 12칼럼 그리드를 정해두고, 한 페이지에 하나만 일부러 벗어남 |
| **디스플레이 세리프** | Bodoni Moda, 자간을 음수로 조여서 |
| **컬러 절제** | 흑백 + 옥스블러드 한 점. 이미 팔레트가 이렇게 되어 있음 |

### 자동 조판이 핵심

**편집기를 주면 안 됩니다.** 사용자는 안 씁니다. 티켓 데이터를 보고 **규칙으로
페이지를 배정**하세요.

```
입력: 올해 티켓 N장
  ├ 표지          — 가장 별점 높은 티켓의 포스터 색 + 연도
  ├ 목차          — 월별 관람 수
  ├ 전면 스프레드 — 사진이 있고 별점 5인 티켓 (최대 3개)
  ├ 그리드 페이지 — 나머지 티켓 6장/페이지
  ├ 통계 페이지   — 장르·장소 분포 (profile_screen 재사용)
  └ 판권          — 발권 번호 목록
```

사용자에게 주는 조절 손잡이는 **템플릿 3종 + 표지 색**정도로 충분합니다.

### PDF 만들기

| 방법 | 장 | 단 |
|---|---|---|
| 페이지마다 `RepaintBoundary → PNG` → `pdf` 패키지로 묶기 | 화면과 100% 동일 | 글자가 이미지라 인쇄 품질 손해, 파일 큼 |
| `pdf` 패키지로 직접 조판 | 벡터 텍스트, 인쇄용으로 정확 | 화면 위젯과 코드가 갈라짐 |

**초기에는 전자**를 권합니다. 단 `targetWidth`를 인쇄 해상도로 잡으세요.
A5 300dpi = **1748 × 2480 px**입니다. 지금 공유 카드의 1080은 화면용입니다.

나중에 서버 렌더러(4번)를 만들면 그쪽에서 벡터 PDF를 뽑고, 앱은 미리보기만
담당하게 나누는 게 깔끔합니다.

### 수익화 지점으로 좋은 이유

연말 결산은 **계절성이 있고 감정이 붙습니다.** 12월에 "2026년 관람 매거진"을
띄우면 그 달에 결제가 몰립니다. 무료는 워터마크 있는 저해상도, Pro는 원본.

## 4. 잉크 — 광고 보상과 해금

> *태그나 광고를 보면 잉크를 지급하고 잉크를 토대로 티켓 디자인이나 스티커를
> 해금하는 구조? 근데 이걸 정확히 어떻게 수익화할지는 고민해봐야할 문제*

### 은유는 맞습니다

"잉크"는 문구류 앱에 잘 붙습니다. 게임 화폐(코인·젬)와 달리 톤을 깨지 않습니다.
잔량을 잉크병 아이콘으로 보여주면 그 자체가 이 앱의 미감입니다.

### 하지만 광고를 주 수입원으로 보면 안 됩니다

숫자로 보면 명확합니다.

```
보상형 광고 eCPM (한국, 2026 기준 대략)  $8 – 15
하루 시청 상한 3회 · 월 20일 활동
→ 유저 1인당 월 광고 수익 ≈ $0.5 – 0.9
```

Articket은 **한 달에 한두 번 여는 앱**입니다. 20일 활동은 낙관적이고 실제로는
월 2–4회일 겁니다. 그러면 유저당 월 수익은 **$0.1 미만**입니다. Pro 구독
₩4,900 하나가 광고 유저 수백 명 몫입니다.

> **광고는 수익원이 아니라 무과금 사용자의 리텐션 장치로 보세요.**
> "돈 안 내도 원하는 스티커를 결국 얻을 수 있다"는 감각이 이탈을 막습니다.

### 잉크를 버는 경로를 광고에만 두지 마세요

이게 설계의 핵심입니다. 광고에만 두면 **앱이 원하는 행동(기록)과 보상이
어긋납니다.** 사용자는 전시를 안 보고 광고만 보게 됩니다.

| 경로 | 지급 | 의도 |
|---|---|---|
| 티켓 한 장 완성 (제목·장소·별점·한 줄 평 다 채움) | 큼 | **핵심 행동** |
| 연속 기록(같은 달에 2회 이상) | 중 | 재방문 |
| 전시 페이지에 티켓 공개 | 중 | 커뮤니티 활성 |
| 보상형 광고 (일 3회 상한) | 작음 | 급할 때 채우는 보조 경로 |
| Pro 구독 | 무제한 | 결제 유도 |

### 잉크로 살 수 있는 것 / 없는 것을 분리하세요

섞으면 회계와 사용자 기대가 둘 다 꼬입니다.

| | 잉크 (소프트) | 현금 (IAP) |
|---|---|---|
| 내장 스티커·프레임·질감 해금 | O | O (묶음 구매) |
| 크리에이터 팩 | **X** | O |
| 매거진 고해상도 내보내기 | X | O (Pro) |
| 실물 인쇄 | X | O |

크리에이터 팩을 잉크로 사게 하면, **크리에이터에게 줄 돈이 없습니다.** 광고
수익으로 정산하겠다는 계산은 위 eCPM 숫자 앞에서 성립하지 않습니다.

### 밸런싱 원칙

소프트 커런시는 **인플레가 나면 되돌릴 수 없습니다.** 지급량을 늘리는 건 쉽고
줄이는 건 폭동입니다. **짜게 시작**하고 이벤트로 푸세요.

그리고 **미성년자**: 보상형 광고는 연령 타게팅과 COPPA/개인정보 이슈가 붙습니다.
앱 연령 등급과 광고 SDK 설정을 맞추세요.

## 5. 실물 티켓 · 매거진 인쇄 배송

> *추후에는 실물 티켓이나 메거진을 만들어서 배송해주는것도 하나의 서비스가
> 될 수 있을것 같다*

### 가장 마지막입니다. 하지만 가장 앱과 어울립니다

"버리지 않고 철해두는 앱"이 결국 종이로 돌아온다는 건 서사가 완결됩니다.
객단가도 압도적으로 높습니다(₩15,000–40,000). 다만 **소프트웨어 회사가 아니라
물류 회사가 되는 결정**입니다.

### 절대 자체 재고를 두지 마세요

POD(Print On Demand) 파트너 API에 붙입니다.

| 지역 | 후보 |
|---|---|
| 국내 | 레드프린팅, 성원애드피아 (API/대량 발주 창구 있음) |
| 해외 | Gelato, Printful (API 성숙, 현지 인쇄로 배송비 절감) |

### 기술적으로 필요한 것 — 서버 렌더러

인쇄용 파일은 앱에서 못 뽑습니다.

| 요구 | 이유 |
|---|---|
| **CMYK** | 화면은 RGB. 그대로 넘기면 옥스블러드가 탁하게 나옴 |
| **300dpi** | 지금 공유 카드는 1080px(화면용) |
| **재단 여백(bleed) 3mm** | 재단 오차로 흰 테두리가 생김 |
| **PDF/X-1a** | 인쇄소 표준 규격 |

그래서 **같은 JSON을 서버에서 다시 렌더**해야 합니다. headless 렌더러(Flutter
Web + Puppeteer, 또는 서버 사이드 Skia/Cairo 재구현)를 하나 만들어 두면
매거진 PDF · 웹 전시 페이지 OG 이미지 · 인쇄 파일 **세 곳에서 재사용**됩니다.

이것이 순서상 **매거진(3) → 인쇄(5)** 인 이유입니다.

### 운영이 진짜 비용입니다

- 통신판매업 신고, 전자상거래법상 청약철회 규정 (주문 제작품은 예외 조항 확인 필요)
- 반품 · 파손 · 오배송 CS. 인쇄 사고는 **반드시** 납니다
- "미리보기와 색이 다르다" 클레임 → 주문 전에 **색상 차이 고지**를 명시적으로
- 배송 추적, 해외 배송이면 관세

### 시험해 볼 가장 싼 방법

풀 서비스를 만들기 전에 **연 1회 한정 판매**로 검증하세요.
12월에 "2026 관람 매거진" 예약 주문을 열고, 수동으로 PDF를 모아 인쇄소에 넘깁니다.
100부가 안 팔리면 시스템을 만들 이유가 없고, 팔리면 그때 자동화합니다.

## 만드는 순서 (권장)

각 단계가 다음 단계의 전제입니다.

```
1. 전시 마스터 DB          ← 지금 안 하면 나중에 못 함
2. 서버 + 클라우드 백업     ← 계정은 이미 있음, 본체만 연결
3. 매거진 PDF 내보내기      ← 서버 렌더러의 첫 사용처. 유료화 1호
4. Pro 구독 + 잉크          ← 수익 기반 확보
5. 전시 페이지 (경량 커뮤니티) ← 1번 위에서만 가능
6. 크리에이터 마켓 A·B등급   ← 5번의 사용자 기반이 있어야 거래가 생김
7. 크리에이터 마켓 C등급     ← SVG 파이프라인 + 모더레이션
8. 실물 인쇄                ← 3번의 렌더러 재사용
```

**4번을 3번보다 먼저 하고 싶은 유혹**이 있을 겁니다. 권하지 않습니다.
팔 것이 없는 상태의 구독은 "왜 돈을 내지?"를 낳습니다. 매거진처럼 **손에 잡히는
결과물**이 하나 있어야 구독이 설명됩니다.

## 기술 스택

| 층 | 선택 | 이유 |
|---|---|---|
| 프론트엔드 | Flutter | 복잡한 커스텀 페인팅과 3D 변환을 크로스 플랫폼으로 |

| 서버 렌더 | headless Flutter Web 또는 Skia (예정) | 매거진 PDF · OG 이미지 · 인쇄 파일 공용 |
| 결제 | StoreKit / Google Billing + IAP | 디지털 재화는 인앱 결제 강제 |
| 실물 인쇄 | POD 파트너 API | 자체 재고 없음 |
